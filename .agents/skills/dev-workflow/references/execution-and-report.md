# 执行、增量验证与交付评估

spec 获批且执行获授权后，或用户明确跳过 spec 并授权实施后阅读。
本规约自包含，不需要外部执行 skill 或额外模式激活。
执行全过程以已批准的统一 spec，或跳过模式下已确认的对话范围、验收、
技术边界和验证方式为基线。纯 UI 将 E2E 义务替换为适用的 UI 验证清单。
面向用户的进度、记录、评估和收尾说明默认用中文；
程序状态值与代码字段保持不变，并给出中文含义。

## 纯 UI 验证适用性

已按入口规约确认的纯 UI 改动，不补写或强制执行新 E2E 方案及测试流程图。
本规约中的必需 E2E、逐节点/关键分支、最终完整流程及相应交付条件，
在该模式下均替换为执行基线中确认的 UI 验证清单；其他授权、评审、CI 与完成条件不变。
用户指定 E2E、仓库必需检查和已有相关回归仍须执行。
实现中出现业务行为或数据链路变化时，停止沿用豁免并补齐 E2E；
默认模式重新评审 spec，跳过模式重新确认对话基线。

本项目默认由用户检查受影响页面、组件和状态，代理完成适用的类型检查或聚焦测试，
并在汇报中列出待用户验收项。用户未提供结果时保持待验证，不以构建通过替代界面验收。
用户明确要求代理执行界面验证时，集中检查布局、文字、可访问性及既有交互，
保留适用尺寸的证据；修复后只重测受影响视图与必要相邻状态，不无理由重复全站流程。

默认模式的评估链接 UI 验证章节，跳过模式引用已确认的对话清单；
两种模式均报告 UI 验收通过数/全部必需项；
E2E 和关键分支覆盖记 N/A 并说明纯 UI 豁免，不虚报 100% 或真实 E2E 已通过。
日志、监控和性能沿用现有机制且未受影响时说明依据，不强制新增埋点；
实际存在的缺口和适用性能验证仍需如实披露。

## 授权与生命周期

权限来自用户的明确批准和交付授权，不来自技能文件。
记录仅本地交付还是允许特定 Git/PR 操作。
本地范围允许约定的实现、验证和修复，不自动授权提交、推送、PR 或合并。
Git 交付只执行获授权的分支/worktree、提交、推送、PR/审查和合并子集；
不从 spec 批准或跳过选择推导缺失权限；本项目阶段提交义务以 `AGENTS.md` 为准，
不将提交要求扩大为推送、PR 或合并授权。

在确认目标与权限范围内，自主拆解必要子任务和选择普通实现细节，不每步再问。
无关改进不进入队列。生产部署、破坏性数据操作、权限/保护/审批设置变更、
以及其他范围外行动需另行授权，宿主执行权限始终适用。

同一会话压缩或恢复时保留授权和进度；新会话重新建立执行授权，
不能将旧检查点当成新的授权。询问状态不代表暂停，明确暂停/停止指令才会中止。
暂停/停止时停止写操作，尽可能取消任务自有待合并动作和唤醒资源，
记录已在进行的操作并保留未完成工作。用户明确要求后才恢复。
当前工作完成不授权无关任务、另一个未批准 spec 或另一项未授权工作。

## 队列与检查点

恢复 clarify 入口的工作区选择。使用该 checkout 实现和验证，
存在批准的 spec 与评审附件时也保留在那里。进入开发时不再创建 worktree，
也不推翻用户拒绝创建的选择；此前创建本身不授权实现或 Git 发布。

按照确认的交付切片形成有序队列。每项注明可用的需求编号、负责模块、
完成条件和验证方法；跳过模式没有编号时使用清楚的验收描述，不虚构编号。
埋点属于实现内容，不是可选收尾；传递基线中的 E2E 或其他验证义务及可用映射。
以内聚架构模块或有意义的模块增量为单位，不以单个函数/文件为单位。
明确依赖顺序和初始主流程验证方法，区分模块初验与最终流程验收。

若选择阶段 PR 模式，将模块任务归入已确认阶段，记录阶段范围、前置阶段、
阶段验收/检查集合和对应 PR。模块完成不自动触发独立 PR；
阶段才是该模式的发布与合并单元。

必需 E2E 证据和交付评估是队列完成条件。
合并/清理会移除所需环境或妨碍修复验收失败时，必须先取得证据。

执行状态、证据位置和验证记录统一维护在 PR 简介中，不写入 `spec.md` 附录、
spec 链接的仓库内执行日志或另一个提交入库的评估报告。spec 只保存需求、设计、
验收标准和测试计划；保留证据采集方法，不填入某次运行结果或产物位置。
PR 简介按交付切片保留当前摘要，避免逐轮流水：

- 阶段、基线类型及版本或对话确认、交付范围、授权范围和当前完成状态。
- 被验证的代码版本、必要环境/夹具、实际命令、结果及通过/失败/跳过数量。
- 对应验收场景、可核验的原始输出或 CI/产物链接、复用证据的适用范围。
- 未执行或失效的验证、缺陷、限制、阻塞和下一步，不将模块初验写成最终验收。
- 当前 head 的检查/审查状态、已确认的批准或合并结果；不沿用旧 head 的结论。

尚无 PR、未获发布授权或仅本地交付时，在任务上下文或 Git 外的恢复记录中暂存；
获授权创建 PR 后再将有关摘要写入简介。不为记录状态创建 PR、提交报告或改动 spec。
队列细节、worktree 选择、自有资源和恢复所需的内部信息也留在任务恢复记录中，
不把无关本机路径、凭据或私密信息发布到 PR。

原始日志、大型生成报告和逐轮执行流水保留在 Git 外或 CI 产物中。
更新 PR 简介时保留已有说明和用户内容，维护当前摘要及证据引用，不另建重复文档。
摘要配合可访问、绑定版本的报告即可，不要求复制已可核验的完整日志。
确认的规划基线与运行记录分开。
追加运行证据本身不改变确认的设计基线，也不触发重新确认。
记录中不存密钥。恢复后比较真实代码/环境和检查点，重新验证受影响证据，
内容与范围未变时不重建 spec、补造 spec 或重复索取批准。
压缩上下文或长时间等待前更新检查点；远程交付恢复写操作前刷新实际 PR head、检查和审查。

## 模块开发与验证节奏

尽量一起完成模块的约定行为、合同、集成调用和关键埋点，再做单元/行为验证。
不要每改一个函数/文件就开启测试循环，也不要把精力分散到无关未完成模块。
模块增量遵循确认的架构边界，“完整模块”不是整套系统全部写完才检查的理由。

初验优先用适合边界的冒烟、单元、集成或行为检查证明主流程。
采用最小有用测试集，必要时补构建、类型或合同检查。
不为覆盖率数字添加穷举细分支，不无理由重跑无关或未变化的测试。

低风险单测细分支可在开发阶段暂缓，记录缺口；
仅当批准验收、具体缺陷或风险需要时补测，不把可选穷举覆盖作为每模块推进门槛。
不删除已有测试、绕过仓库必需检查、漏测已知回归，
也不将基线中的关键 E2E 结果重新定义为可选。
具体阻塞、共享合同不确定或高风险行为可提前做针对性检查，遵守仓库强制测试节奏。

模块完成并初验通过后及时：

1. 更新已授权 PR 简介中的当前执行摘要，记录范围、源码标识、实际检查结果、
   证据和暂缓覆盖；无 PR 时更新任务恢复记录，不修改 spec。
2. 用中文简要汇报已完成模块与行为、初验结果、重要缺口/阻塞和下一模块。
   在开始下一模块或长时间等待 PR/CI 前报告。
3. 继续已授权队列，不再询问是否推进。

完整流程未测时称“已实现并初步验证”，而不是“已全部验收”。
检查失败或无法运行时报告真实失败/阻塞，不虚报里程碑。
进度更新和用户汇报不自动授权 PR 编辑、Git 提交、
外部 tracker 写入或向其他聊天发消息；仍受已有交付授权约束。

## 自主交付循环

对队列中每个就绪交付单元执行以下循环。
阶段 PR 模式中交付单元是阶段，阶段内模块继续遵循前述开发与初验节奏：

1. **实现与验证**：阅读项目指令和既有机制，保留用户无关改动。
   按仓库规则复用合适 checkout 或任务 worktree，明确资源所有权。
   完成约定行为与埋点，同步受影响文档。
   遵循模块完整开发、主流程优先验证的节奏，初验通过后立即汇报。
   仅在可用且获授权时使用独立 agent。重复缺陷揭示结构问题时重审设计，
   实质基线变化需重新确认；默认 spec 模式还需修订并重新批准文档。
2. **授权后发布**：Git 交付按授权子集提交/推送聚焦改动并创建/更新 PR。
   使用已配置 Git 身份与仓库惯例，不添加 AI co-author 署名。
   在任务分支整合必要主线更新，解决冲突后重新验证。
   纯本地交付不推送、不创建 PR、不合并，仍遵守本项目阶段提交要求。
3. **处理适用 CI 和审查**：跟踪实际远程 head，读取失败日志和意见。
   获授权时使用仓库既有审查机制。根据执行基线独立判断意见，
   修复引入的 Critical/Major 问题及使交付错误的缺陷，不盲目采纳。
   记录修复/延后/拒绝的处理结论，在原意见线程中标明 agent 身份和理由，
   按仓库规则解决线程。较小无关改进单独延后。
   每次推送刷新检查与审查状态，直到无新 Critical/Major 问题且当前 head 要求满足。
4. **有权限且就绪才合并**：刷新 head SHA、必需检查、阻塞线程、可合并状态，
   以及针对当前 head 的真实 reviewer 批准。
   当前交付单元的验收证据和适用关卡通过后才能合并。
   不把沉默当批准、不自批、不绕保护、不弱化检查、不用管理员强制覆盖。
   使用仓库允许的合并方法，平台支持时绑定已核验 head；head 变化则重查。
   确认平台报告已合并并记录最终 commit，auto-merge 请求或队列排入不是合并完成。
5. **记录并推进**：更新任务与证据状态，直接继续下一就绪项。
   除非确认计划允许并行，每项约定交付完成后才开始下一项。
   保留未执行 E2E 所需的共享夹具和环境。

创建 PR、检查仍运行或请求了审查都不是完成。
未授权合并时停在约定交付边界，不因平台允许就主动合并。
本地交付按真实产物与验收验证，不新增远程审批关卡。

已授权的 CI/审查等待仍是工作。使用有界 watch 或合理退避轮询；
watch 超时不表示任务完成。处理新结果，不反复读取未变化状态。
长等待只有在真实续跑机制可用且获授权时使用；
没有机制不得宣称后台持续监控，也不创建无关周期任务。

仍有有用且获授权行动时持续推进。
只有重要未决选择、凭据、外部权限、必需 reviewer 不可用或其他真实阻塞时请求介入。
记录具体阻塞、最小介入要求和下一步，区分阻塞与完成；
不再次请求已经授予的常规权限。

## 可选模式：每阶段一个 PR

用户选择并授权后使用本模式；不要自动将所有任务改成分阶段 PR，
也不要替纯本地任务新增远程交付。
在执行基线中确认阶段、模块范围、阶段验收、顺序和最终完整流程义务；
默认模式记录在同一个 spec 中，跳过模式记录在对话确认中。
一次授权可覆盖约定队列内各阶段的常规发布、评论修复和合并操作，
但不授权范围外需求、生产部署或绕过审批。

执行链路为：

`当前阶段开发 -> 阶段验证 -> 提交 PR -> 监控 CI/评论/审查 -> 必要修复与回归 -> 当前 head 获批 -> 确认合并 -> 下一阶段`

### 阶段发布与监控

- 阶段内先完成各模块及必要主流程验证，及时更新模块进度。
  阶段完成后汇总聚焦改动形成一个 PR，描述阶段范围、可用的 spec/需求编号或对话基线、
  实际验证和剩余的后续阶段义务。
- PR 提交后立即开始跟进，通过已有平台工具或 CLI 获取真实状态。
  同时查看 head SHA、必需检查、普通 PR comments、review comments、
  阻塞线程、changes requested、真实 reviewer 批准和可合并状态，
  不把“没有新评论”或 CI 通过当成批准。
- 对每条新评论判断修复、延后或拒绝，处理与阶段范围有关的必要问题，
  在对应线程说明改动或理由。必需阻塞意见必须解决，不能仅忽略评论就推进。
  修复后运行失败项和最小必要回归，按需要更新阶段证据和描述，再推送改动。
- 每次新推送刷新当前 head 的 CI 与审查，不能用旧 head 的通过/批准证明新版本就绪。
  记录已处理评论标识及最新状态，避免反复回应相同意见或读取无变化快照。
- CI 或 review 尚未完成时继续有界等待与处理，不在 PR 创建后就宣称任务完成。
  仅在真实续跑机制可用且获授权时使用它，不声称无工具支持的后台监控。
  用户暂停/停止时按生命周期规约处理待合并和续跑资源。

### 合并后再推进

合并前刷新状态，要求当前 head 的真实批准、阶段必需检查通过、
阻塞线程已处理和可合并，并仍具有合并授权。
条件满足后直接按仓库允许的方法执行合并并核对结果，
不在 approved 状态停工或重复询问已授权操作。
不自批、不绕保护、不强制管理员合并。确认平台确实报告已合并，
记录最终 commit；仅 approved、auto-merge 请求或进入合并队列都不足以完成阶段。

确认合并后再获取目标分支最新状态，以包含该合并的最新目标分支作为下一阶段起点，
在已选工作区和获授权分支中继续。不要每阶段自动创建新的 worktree，
也不开始基于未合并阶段的下一阶段实现或 PR；需要并行或 stacked PR 时，
先让用户明确改选交付模式。
无需为常规进入下一阶段再次询问，也不自动增加合并后主线 CI 等待。

PR 被关闭但未合并、缺少合并权限、必需 reviewer 不可用或其他真正阻塞时，
说明当前阶段尚未交付，解决阻塞或请求最小介入；不能将后续阶段当作绕过关卡的方式。
一阶段的 CI/验收只覆盖该阶段，不虚报整个 MVP 已通过。
暂未实现的后续 E2E 保留为未执行义务，在最终阶段关闭前完成
执行基线要求的完整流程验证和评估；不为每个阶段重跑无关的全套 E2E。

## 完整流程验证

实现后，至少一次用可用证据覆盖每个必需 E2E 场景及关键分支结果。
开发中的针对性检查不能替代完整工作流验证。
检查基线中的各项通过标准，包括适用的节点及核心调用日志/telemetry，
不能只看最终页面或响应。

在 PR 简介中汇总场景状态，并引用详细原始证据；无 PR 时保留在任务记录中。
不要将实际结果填回 spec 的测试计划。结果映射可用：

`E2E-ID | NODE/REQ/BR 编号 | 版本/环境/夹具 | 结果 | 断言/证据 | 缺陷 | 证据有效性`

程序状态保留原值，并附中文含义：

- `not-run`：未执行。
- `passed`：通过。
- `failed`：失败。
- `blocked`：受阻。
- `invalidated`：旧证据失效。
- `reused-valid`：经过影响分析仍有效的历史通过证据，注明复用理由和原 run 标识，不称为新运行。

每项通过都需要真实断言结果及 runner 输出、截图、trace、数据库检查、
日志或指标样本等证据。stub、不可达服务、凭据缺失、跳过用例和不稳定结果必须披露，
说明真实性限制。不把未测结果写成通过，也不降低断言来过关。

## 修复后不从头重跑

场景失败时：

1. 保留失败断言、复现、代码/环境标识和诊断证据，先分清产品、测试、
   夹具/环境或暂时性基础设施问题。
2. 修复根因并分析影响：模块/合同、调用方、数据、共享基础设施、
   场景依赖及可观测性。
3. 重跑失败场景及最小充分回归集，包括改变的分支和合同消费者；
   适合的细边界可用聚焦低层测试。
4. 让假设发生变化的旧通过失效，保留无关且仍有效的证据并写明理由，
   随后继续未执行场景。依赖步骤前恢复确定性夹具。
5. 持续到全部必需义务有有效最终证据，或确有外部阻塞需要介入。
   修复暴露结构矛盾时重审架构，不无限堆补丁。

影响记录可使用：

`修复/版本 | 根因 | 改动边界 | 重跑编号与理由 | 保留证据与理由 | 剩余工作`

仅修改视图显示通常测失败场景及相邻视图，不重复无关导入链路。
授权、共享序列化器、数据库 schema、事件传递、全局配置或共享夹具改动可能影响广泛，
无法证明独立性时扩展跨端回归或完整流程；运行前解释扩大范围的原因。

不绝对禁止全量重跑。必需 CI 保留，广泛变化有时确实需要全量。
原则是避免每次修复都无必要重启完整流程，不是保留过期证据或跳过未执行义务。
验收要求最终构建单次连续旅程时，必须真实端到端执行；
碎片化检查不能替代。其他情况也只有影响分析证明旧证据对最终版本/环境有效时才可组合。

不盲目重跑到绿；暂时性失败必须有依据。
同一根因经历三次修复仍无新证据或进展时，停止重复原方法并深入诊断，
确有决定、权限或环境阻塞时说明。不得承诺无限无人值守循环或去掉审批关卡。

## 最终评估

在 PR 简介的交付评估中给出中文结论，不生成 spec 同目录的 `evaluation.md`，
不新增 spec 执行附录或仓库内报告。仅本地交付时在任务汇报中提供同样的评估。
总判断保留 `complete`（完成）、`partial`（部分完成）、`blocked`（阻塞）等状态，
并解释含义。
包括批准范围/版本、实际实现版本、环境、证据日期，
以及可用的 spec 需求/技术/E2E 章节或对话基线说明、源码和运行产物链接。

分别评估：

| 维度 | 核查证据 | 必须披露 |
| --- | --- | --- |
| 需求 | 每项可用的验收编号或验收描述、实现行为与通过断言 | 逐项已验证、部分完成、缺失或未验证 |
| 架构 | 实际模块/依赖、合同、状态所有权、跨端数据流 | 一致、合理偏差、违反或未验证；实质偏差是否重新确认 |
| 测试 | MVP、基线中的场景/通过标准、关键分支结果及有效 run 证据 | 通过/失败/受阻/未执行数量和缺口 |
| 日志 | 成功、错误、慢路径、安全字段和关联传播 | 代码埋点与真实日志证据分别说明 |
| 监控 | 导出指标/trace、可用视图、告警和负责人 | 已实现、已观察、已配置未验证、缺失或有依据的不适用 |
| 性能 | 已定义负载/环境、实测与约定预算 | 分位数、吞吐/资源结果、达标/不达标或未测基线缺口 |

明确分母：

- 需求完成度：已验证验收标准 / 范围内全部标准。
  一个需求含多个标准时，全部通过才能称该需求完成。
- E2E 场景覆盖：有有效通过证据的必需场景 / 全部必需场景，
  分母包含失败、受阻和未执行。
- 关键分支覆盖：已验证必需结果 / 执行基线所选分支的全部必需结果。
  说明清单是风险选择，不是穷举源码分支。
- 代码行/分支覆盖：只使用真实覆盖工具结果，注明源码范围、命令、版本和产物；
  未测则写 `not measured`（未测量），不估算。

分母为零时写 N/A 并解释，不能报 100%。
呈现分子、分母和状态，不虚构综合分数或用百分比掩盖阻塞。
区分建议、已批准和实测性能值；无实测是未验证，不是“足够快”。

说明缺陷与聚焦回归、旧证据仍有效的原因、设计偏差/批准、残余风险及延期影响。
暂缓单测细节与必需 E2E 义务分开；模块冒烟不替代最终流程验收。
可观测性缺口分别说明缺代码、缺后端/配置还是缺运行验证，
埋点调用不证明告警或仪表盘正常工作。

必需场景仍失败、受阻、未执行或失效时，不宣布完整流程完成。
用户批准缩减范围需记录新基线，不静默从分母移除。
评估摘要不是未完成测试的替代品。

## 收尾与清理

每项队列达到批准范围完成条件后，报告已验证结果、PR 简介中的评估位置（或本地任务汇报）、
相关 PR/合并 commit、残余限制和延期项，不把未完成验证称作交付。
阶段 PR 模式还需汇总各阶段的 PR、真实合并 commit 和验收结果，
确认所有约定阶段已合并且最终 E2E/评估义务满足。

确认合并后，未经用户明确要求，不等待额外主线 CI；约定的关闭前验证仍然适用。
各交付模式都保留必要产物，只清理不再需要的任务自有临时文件、服务、worktree、
唤醒和待执行动作，同时检查失败 agent 留下的资源。
使用可恢复的 worktree 清理机制，保留用户工作。
