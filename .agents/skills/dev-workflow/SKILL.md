# 开发工作流

将用户需求转化为经评审的设计、经过验证的实现和可信的交付评估。
文档深度与任务规模相匹配；架构描述职责与边界，不堆砌类和函数清单。

## 本项目适配边界

本技能的通用流程服从适用的 `AGENTS.md` 和宿主指令，两种 spec 模式均不例外。
本项目 UI 验收默认由用户执行，不因下文的截图、浏览器或 E2E 示例自动启动界面验证；
规划时区分代理负责的代码级检查与用户负责的 UI 验收，未反馈的验收保持待验证。
阶段提交遵守仓库要求，推送、PR 和合并仍按授权范围执行；影响主要产品链路的改动
遵循功能分支 -> `beta` -> `main`，阶段 PR 的下一阶段起点不能绕过该集成路径。
子 agent 的每次委派均须单独取得用户批准，并显式选择 Luna 系列模型。

## 中文输出约定

默认使用简体中文进行需求澄清、技术方案讨论、评审请求、进度汇报和最终答复。
`spec.md`、评估报告、图表标题、节点说明、分支标签及 HTML 预览中的自然语言均使用中文。
仅在用户明确要求其他语言时调整。

技能名、文件路径、命令、代码标识、协议字段、JSON 键、需求编号和状态枚举保持原样。
技术名词可保留原文，例如 Mermaid、worktree、E2E、telemetry；第三方原始错误和引用保留原文，并用中文解释。
不要为了翻译改动 API 合同或程序可识别的值。

## 阶段与授权

默认阶段顺序：

`clarifying -> designing -> planning-e2e -> drafting -> awaiting-review -> approved -> implementing -> verifying -> assessed`

spec 生成包含三个核心步骤：明确需求（`clarifying`）、确认技术方案（`designing`）、
构建 E2E 流程（`planning-e2e`），随后整理并评审完整文档。
纯 UI 改动适用下方例外：跳过 `planning-e2e`，确认技术方案后直接整理 spec。
反馈改变范围或决定时，返回受影响步骤；工作草稿不等于已批准方案。

用户明确选择跳过 spec 时使用：

`clarifying -> direct-planning -> implementing -> verifying -> assessed`

`direct-planning` 在对话中确认实现基线，不生成或评审 spec 及其图表附件。
跳过 spec 不等于跳过技术设计、测试规划、验证或交付评估。

确有外部依赖阻止推进时记录 `blocked`，保留当前阶段、阻塞原因和下一步，便于恢复。
创建或修改本技能不意味着授权产品开发或交付。

默认模式下，统一 spec 获明确批准之前，只允许阅读项目和编写规划内容，不得实现产品代码、
搭建项目、安装实现依赖或启动实现 agent/skill。改变验收或架构的未决事项会阻止批准；
普通实现细节不需要逐项表决。

批准前可生成规划图与评审页面，这属于文档工作，不是实现授权。
也可在用户明确确认后创建 worktree，但该确认不授权开发、提交、推送或合并。

本技能内置自主执行规约，不依赖另一执行 skill。
用户批准 spec 并授权交付范围，或明确跳过 spec 并授权按对话基线执行后，
在该范围内持续推进，不重复询问常规步骤是否继续。
spec 批准或跳过本身都不授予 Git 发布或合并权限；始终遵守更窄的用户指示和宿主权限。
技能文本本身不提供任何额外权限。

## spec 默认与跳过

默认生成、评审并批准统一 spec。不要主动把任务降级为无 spec，也不因改动小、紧急、
需求看似清楚或用户只说“实现”而推断跳过。用户明确表示“跳过 spec”“无需 spec”
或等价意图时，才对当前任务采用跳过模式；该选择不自动延续到其他任务。
不需要每次询问是否跳过，未选择时直接按默认流程推进。

跳过模式免除的是本技能创建 `spec.md`、`.mmd`、HTML/PNG 评审附件和文档批准关卡。
开始实现前，仍应在对话中形成足够清楚的执行基线：目标与范围、可观察验收、
关键技术边界、验证方式，以及会阻止正确实现的未决事项。内容按风险保持简洁，
不把对话摘要变相扩写成完整 spec。用户在同一条指令中明确跳过 spec 并要求实现，
可同时构成跳过选择和本地执行授权；只说跳过 spec 不自动授权写代码。

已有适用 spec、仓库合同和用户先前确认仍然有效，不能因跳过新 spec 而忽略。
跳过模式不免除仓库必需检查、用户指定测试、风险所需的 E2E、权限边界或真实证据。
实现中出现会改变目标、验收、架构边界或关键验证义务的事项时，先在对话中重新确认；
若用户改回 spec 模式，则按默认流程整理和评审后继续。

## 纯 UI 改动例外

澄清时依据实际改动判断；默认模式在 spec 记录，跳过模式在对话基线确认：
仅调整样式、布局、文案、图标或展示，
不改变业务行为、交互状态流转、数据读写、接口合同、权限或跨端同步时，属于纯 UI。
只修改前端文件不等于纯 UI；范围混合或无法确认行为未变时，仍按常规流程规划相关 E2E。

纯 UI 不要求生成 E2E 测试方案、测试流程图或 `<feature-name>-test-workflow.html`，
不为此安装测试流程渲染依赖。spec 第三章改为“UI 验证”，简列验收点与证据采集方式：
受影响页面/组件和状态的预览、适用的桌面/移动尺寸、文字与溢出、
可访问性及既有交互未回归。可采用截图、浏览器检查或已有组件/视觉测试，
不强制新增 E2E 用例。技术方案及适用架构图要求不因该例外自动取消。

开发、评估及完成关卡以获批 UI 验证清单代替 E2E/节点/分支义务；
E2E 覆盖写 N/A 并说明理由，不报为已通过。未受影响的日志、监控和性能机制
沿用现状，不为纯展示调整强行新增埋点；有依据的不适用项应说明。
仓库必需检查、已有相关回归及用户明确要求的 E2E 不得跳过。
发现改动涉及行为或数据链路时，撤销例外并补齐受影响 E2E 方案；
默认模式重新评审 spec，跳过模式在对话中重新确认基线后继续。

## 图表渲染依赖

评审图依赖 Mermaid CLI（`@mermaid-js/mermaid-cli`，命令 `mmdc`）、
其支持的 Node.js 运行时，以及可用的 Puppeteer/Chromium 浏览器。
Python 3 运行本技能的 HTML 打包脚本。优先复用已安装工具；
安装或下载依赖仍需相应权限。

渲染前阅读 [图表渲染规约](references/diagram-rendering.md)。
工具缺失或运行失败时说明真实情况，不得静默用 Mermaid 源码代替渲染成果。

## 一、默认分三步生成 spec

开始澄清前阅读 [需求、设计与测试规约](references/design-and-test.md)。
先检查适用项目指令、现有架构、相关代码、测试、文档和近期变更，复用已有回答和决定。

步骤一开头的工作区选择适用于两种模式。除此之外，以下三步、图表与文档要求
适用于默认 spec 模式。跳过模式改用参考规约中的轻量规划，
保留必要澄清、技术判断与验证设计，不创建这些文档产物。

通过对话逐步收敛，不一次抛出整套问卷，也不依据猜测直接生成完整 spec。
每轮聚焦影响最大的一个未决问题，等待真实回答。将阶段产物分成易于讨论的片段，
确认后再进入下一核心步骤。区分已确认事实、用户选择、助手建议和未决假设；
不重复询问已确定内容，也不人为制造疑问来延长讨论。

### 步骤一：明确需求

初次进入 clarify 时，在具体需求问题或规划文件写入之前，先询问：
“是否需要为本次任务创建一个新的 Git worktree？”
用户已明确表达选择时直接复用，不在澄清回环或同一任务恢复时再次询问。

只有明确确认才创建。优先使用宿主管理的 worktree 工具，等待创建成功，
然后使用返回目录进行后续规划和开发。未确认则留在当前工作区，不创建新的 worktree。
记录选择及实际目录，并遵循 [工作区选择流程](references/design-and-test.md)；
不得将失败或仍在进行的创建操作当成已成功切换工作区。

明确目标、用户和平台、端到端 MVP 主流程、范围内外行为、业务失败规则、
约束及可观察的成功标准。范围较大时先讨论模块边界和交付顺序。
记录用户指定的技术约束，但不要在理解问题之前锁定尚未选择的方案。

产物：带稳定验收编号的目标与需求。简要复述并确认用户意图；
重要需求缺口解决后再进入步骤二。

### 步骤二：确认技术方案

根据已确认需求与项目现状选择方案。针对重要未决选型，比较 2–3 个可行方案、
说明取舍并给出建议，获得用户选择后才视为确定。
保留用户指定技术和合理的既有模式，不为凑选项重新选型。

讨论架构图、模块边界、数据或调用流向、关键合同，以及日志、telemetry 和性能设计；
不添加无实际必要的基础设施。

使用 Mermaid CLI 渲染架构，并生成 `<feature-name>-dev-design.html` 供本阶段评审；
需要时生成 PNG 预览。产物是已确认的技术方案、渲染后的架构图和重要决策。
进入步骤三之前，确认完整设计，而不只是框架或数据库名称。

### 步骤三：构建 E2E 测试流程

纯 UI 按例外确认 UI 验证清单，不进入本步骤，也不生成测试流程附件。
同时依据已确认需求和技术方案形成 E2E 计划。
讨论完整 MVP 链路、关键条件分支、测试流程图、每个节点的通过标准、
所需环境和证据。将需求、架构边界映射到场景，并纳入核心调用的日志和 telemetry 验证。

使用 Mermaid CLI 渲染流程，生成 `<feature-name>-test-workflow.html`；
同一页面包含所有关键子流程，必要时导出 PNG。
产物是已确认的 E2E 流程及验收映射。确认它能证明预期行为后再整理完整 spec。
渲染测试计划不等于执行产品测试。

复用已有明确确认作为各步骤关卡。反馈改变早期决定时，返回最早受影响步骤，
同步修订下游设计和测试；保留不受影响的确认，不从头重走所有步骤。

## 二、整理统一 spec

本节只适用于默认 spec 模式。
设计收敛后，根据参考规约将确认内容整理到一个文档中。
采用项目现有目录约定，否则使用：

```text
docs/dev-workflow/YYYY-MM-DD-<topic>/spec.md
```

适用的 HTML 附件放在 spec 同目录；纯 UI 只需开发设计附件。技术方案章节链接开发设计页面，
E2E 章节链接测试流程页面，也可嵌入 PNG 方便预览。
spec 中保留可编辑的 Mermaid 源码及完全匹配的 `.mmd` 文件；
源码变更后重新生成受影响附件，提交评审前核对链接、预览和当前源码。
附件是评审视图，不是独立规划文档。

所有需求、技术设计和 E2E 计划必须放在同一个 spec，不单独生成 E2E 规划文档。
spec 必须有以下三个清晰可辨的中文章节；纯 UI 将第三章替换为“UI 验证”：

1. **目标和需求描述**：目标、MVP 主流程、范围、约束，以及带稳定编号的可验收需求。
2. **技术方案**：技术选型、模块职责、层次边界和架构图。
   多端系统说明客户端与服务之间的数据传递方向及返回路径；
   单端内部处理说明核心模块之间的调用及数据返回，不凭空添加网络架构。
   建议说明关键通信协议和必要接口合同，并设计核心调用的日志、监控与性能统计。
3. **E2E 测试方案**：同时依据需求和架构，包含完整 MVP 主流程和关键条件分支的流程图。
   每个图节点必须有可观察的通过标准，可写在标签或关联的节点编号表中。
   映射节点、分支、场景和需求编号，说明夹具、环境及依赖真实性。
   非关键分支可省略或合并，关键分支不能只藏在文字或表格里。
   包含核心日志、telemetry 统计及适用性能行为的检查。

评审前自查矛盾、责任缺失、关键分支遗漏、模糊验收及图文不一致，先修正再提交。
区分估计、建议性能预算和已约定要求。
分段反馈不代替完整书面 spec 评审；用户要求修改时，联动更新需求、设计和测试，
再次自审并提交实际修订文档。

## 三、用户评审关卡

默认 spec 模式按本节完成文档评审。
分阶段开发时，可选择“每阶段一个 PR”，也可使用用户确认的其他交付方式。
在 spec 中明确阶段边界、包含模块、依赖顺序和阶段验收条件，并确认交付模式。
选择阶段 PR 模式时，明确提交、推送、创建/更新 PR、回应审查及合并的授权范围；
不得从文档批准推导这些权限，也不强迫纯本地任务使用 PR。

给出完整 spec 的可点击链接，概述重要决定及未决事项。
分别明确文档批准和交付授权的含义，例如：

> 请评审 spec.md 中的目标与需求、技术方案和 E2E 测试方案。
> 是否批准这份 spec，并授权在约定范围内自主完成开发、测试、修复和交付？
> 请确认仅本地交付，或已提出的提交、推送、PR、审查和合并范围。

纯 UI 的评审请求使用“UI 验证”，不索要不存在的 E2E 章节或流程图。
只提出适合仓库和用户请求的交付方式。
一次明确回复可同时批准完整 spec 和所描述的执行范围，不需要额外激活另一模式。
仅批准某一节、沉默或指代不清的“看起来不错”，不等于批准完整文档及执行权限。
只有文档获批时，保留批准，只询问缺少的执行授权；有效的会话授权不重复请求。

在 PR 简介中记录获批版本或内容标识、用户确认、范围及条件，不写入 spec 执行附录。
尚无 PR 或仅本地交付时，保留在任务上下文或 Git 外的恢复记录中；
不为记录状态擅自创建 PR。spec 只保存需求、设计决定、验收标准和测试计划，
不保存执行状态、证据位置、验证记录或逐轮运行流水。
验收行为、架构边界、交付范围或关键测试义务发生实质变化时，
重新评审修订后的 spec；不得降低标准来让测试通过。

跳过模式没有文档批准关卡。开始实现前，确认对话基线和执行授权已经明确；
用户已在同一指令中清楚给出时直接复用，不要求再回复一次“批准”。
只确认跳过而未要求实施时，继续澄清或等待实施授权。

## 四、开发与验证

关卡通过后阅读 [执行与评估规约](references/execution-and-report.md)，直接执行内置规约。
默认模式按照批准的 spec 路径、章节、验收编号、架构约束、验证义务、
授权范围和完成条件组织任务队列；跳过模式按照已确认的对话基线组织，
不虚构 spec 路径或编号。

若用户选择“每阶段一个 PR”，阶段内按模块推进并及时汇报，
阶段完成后汇总相关改动创建一个 PR，而不是为每个微任务单独创建。
持续监控该 PR 的 head、CI、普通评论、审查意见和批准状态，
判断评论是否需要修复，按影响范围修改、回归并回应。
修复推送后重新核对当前 head 的检查和审查，不沿用已过期批准。
只有当前 PR 获真实批准、必需检查通过且平台确认已 merge，
才从最新目标分支推进下一阶段；PR 已创建、approved 或进入合并队列均不等于阶段交付完成。
等待中持续处理新结果，出现真实权限、审批或环境阻塞时记录并请求最小介入。
一个阶段合并不代表整个功能已验收，最终完整 E2E 和评估义务仍保留。

尽量完整实现一个内聚的架构模块，再集中进行必要的单元或行为验证，
不要每次小改动都测试，也不要在多个无关的未完成模块之间来回切换。
优先主流程冒烟检查及最小必要测试集，暂缓低风险细分支，
不构建无必要的穷举单测矩阵或反复运行未变化的测试。
解决具体阻塞、高风险不确定性或仓库强制要求时，可以提前做针对性检查。

模块完成并初验通过后，及时更新已授权 PR 简介中的执行摘要（无 PR 时更新任务记录），
并用中文简要报告完成范围、实际检查结果、暂缓覆盖和下一个模块。
在切换模块或等待长时间交付检查之前报告，
不为常规继续执行再次征求批准。
这只是模块里程碑，不代表最终 E2E 验收通过，也不新增 Git 权限。
暂缓单测细节不能静默取消基线中的关键分支、回归检查或必需 CI；
在适当阶段完成这些义务。

持续完成开发、适用 CI/审查修复、按影响范围回归和未执行的 E2E 场景，
直到范围内工作经过验证并交付，或出现需要介入的真实阻塞。
用户要求暂停或停止时保留恢复检查点。不要询问是否继续已授权工作、
扩大范围或给本地交付凭空增加 PR 要求。
仓库必需检查始终保留，关闭前完成约定验证；
未获用户要求，不新增合并后主线 CI 等待。

## 五、评估与收尾

在 PR 简介中更新中文交付评估，遵循执行参考中的评估规则；
仅本地交付时在任务汇报中提供。不再要求生成 spec 同目录的 `evaluation.md`，
也不把评估或验证记录追加到 spec。
分别评估需求完成度、架构一致性、测试覆盖、日志、监控和性能证据。
链接源码位置及运行产物，明确缺口、阻塞检查、偏差和未知项。
不能把已写代码、测试计划或 mock 运行当成实际证明。

只有约定范围、完整流程覆盖和适用交付关卡均满足，且交付评估已记录，
才报告完成；否则说明真实的部分完成或阻塞状态，以及剩余事项。
